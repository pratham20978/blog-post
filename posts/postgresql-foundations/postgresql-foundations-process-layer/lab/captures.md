## 7. When autovacuum decides a table needs vacuuming

The threshold is `autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples`, compared against the statistics collector's estimate of dead tuples. Nothing here is hypothetical: the numbers are read out of `pg_settings` and `pg_class` and the comparison is done in SQL.

### The three thresholds, computed

```sql
select c.relname,
       c.reltuples::bigint as reltuples,
       current_setting('autovacuum_vacuum_threshold')::int as base,
       current_setting('autovacuum_vacuum_scale_factor')::float as scale,
       (current_setting('autovacuum_vacuum_threshold')::int
        + current_setting('autovacuum_vacuum_scale_factor')::float * c.reltuples)::bigint
         as vacuum_threshold,
       (current_setting('autovacuum_vacuum_insert_threshold')::int
        + current_setting('autovacuum_vacuum_insert_scale_factor')::float * c.reltuples)::bigint
         as insert_threshold,
       (current_setting('autovacuum_analyze_threshold')::int
        + current_setting('autovacuum_analyze_scale_factor')::float * c.reltuples)::bigint
         as analyze_threshold,
       s.n_dead_tup, s.n_ins_since_vacuum, s.n_mod_since_analyze
from pg_class c join pg_stat_all_tables s on s.relid = c.oid
where c.relname in ('customers','orders');
```


## 8. The number that decides how long a vacuum takes

`maintenance_work_mem` holds the list of dead tuple identifiers. When the list fills, vacuum must stop, scan **every index in full**, empty the list and resume the heap scan where it left off. So the memory setting does not make vacuum a little faster: it multiplies the number of complete index scans. Same table, same deletion, two settings.

## 12. Cancel and terminate are two different signals

A session runs `pg_sleep`. `pg_cancel_backend` ends the statement and leaves the connection alive; `pg_terminate_backend` ends the process. The first arrives as SIGINT, the second as SIGTERM; both only set a flag that the next `CHECK_FOR_INTERRUPTS()` acts on.

```text

  "after_cancel_connection_usable": "still here",
  "after_cancel_rows_in_pg_stat_activity": 1,
  "after_terminate_rows_in_pg_stat_activity": 0,
  "cancel_error": "canceling statement due to user request",
  "terminate_error": "terminating connection due to administrator command"
}
```

## 15. What the postmaster does when one child dies badly

A backend is killed with SIGKILL. It cannot run its cleanup, so shared memory may be inconsistent, and the postmaster's only safe move is to terminate every other backend and run crash recovery. Watch the log.

