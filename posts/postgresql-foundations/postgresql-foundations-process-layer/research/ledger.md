# Source ledger — postgresql-foundations-process-layer

Research ran 2026-09-19. Two attempts at a parallel research fan-out failed on session
limits; the research was then done directly against the PostgreSQL 16 documentation, the
release notes for 10, 14, 15, 17 and 18, and a local copy of the `REL_16_2` source tree
(with `REL_17_0` and `REL_18_0` files where a mechanism changed). Source-code citations
name the file and function. The post's live examples were captured on PostgreSQL 16.2, so
every version-dependent claim names the version it holds for; "current" means the 18.x
docs as fetched on the access date.

Two lab findings corrected the brief's own assumptions and are recorded as claims rather
than hidden: `pg_cancel_backend` is SIGINT and `pg_terminate_backend` is SIGTERM (not
ProcSignal), and auxiliary processes have been in `pg_stat_activity` since 10, not 14.

## Claims

| Key | Claim (our words) | Source | Condition |
|---|---|---|---|
| L01 | The postmaster creates shared memory and semaphores at startup but as a rule does not touch them afterwards; it is not in the PGPROC array and cannot take locks. Keeping it out of shared memory is what lets it survive and reset after a backend crash. | S21 file header | all versions |
| L02 | On a connection request the postmaster forks immediately; the child performs authentication and then becomes a backend. This keeps auth code single-threaded and stops a blocked SSL or PAM library from denying service to other clients. | S21 file header | Unix; Windows uses EXEC_BACKEND |
| L03 | When a child exits abnormally the postmaster logs it, logs "terminating any other active server processes", sends SIGQUIT to every other child, and reinitialises shared memory before accepting connections again. | S21 `HandleChildCrash`; S46 step 15 | `restart_after_crash = on` (default) |
| L04 | The lab's SIGKILLed backend produced exactly that sequence: "terminated by signal 9", "terminating any other active server processes", "all server processes terminated; reinitializing", then crash recovery from the last redo point; an innocent second connection was disconnected with "server closed the connection unexpectedly". | S46 step 15 | PostgreSQL 16.2 |
| L05 | The checkpointer's and WAL writer's file headers say an unexpected exit of either is treated the same as a backend crash, because shared memory may be corrupt and, for the checkpointer, the list of files needing fsync is lost. | S28, S31 file headers | all versions |
| L06 | `fork_process()` is a thin wrapper over `fork()`. | S40 | Unix |
| L07 | `MaxBackends = max_connections + autovacuum_max_workers + 1 + max_worker_processes + max_wal_senders`; with defaults that is 100 + 3 + 1 + 8 + 10 = 122 PGPROC slots. | S38 `InitializeMaxBackends` | PostgreSQL 16 |

## Open questions

- Whether autovacuum ever uses parallel index vacuuming. The VACUUM reference does not say
  either way; the source (`vacuum.c`, `vacuum_rel`) passes `nworkers = -1` for autovacuum in
  16, which disables it. The post states it as "autovacuum does not use parallel vacuum in
  16" citing the source path, and flags it as source-derived.
- The exact "logarithmic" rule for the planner's worker count lives in
  `compute_parallel_worker()` (`allpaths.c`): one worker at `min_parallel_table_scan_size`,
  one more for each tripling. The doc page for 16 does not spell out the tripling, so the post
  says "roughly one more worker each time the table triples" and cites the source.
- Heikki's thread's *reasons* for threads (memory sharing, cheaper connections) are in later
  messages of the thread, not the first; the post cites only what the first message says.
